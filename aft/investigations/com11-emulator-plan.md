# COM11 SAS host/poll emulator — architecture, evidence, and staged plan

Goal: bring the `10.0.0.171` SAS session **online and sustained** so
`GoldClub.Aurum.Services` (WAT2AFT) finds an **owned device** and an AFT credit
commits — by restoring the missing **host general-poll stream (`80`/`81`)** that
`.90` has and `.171` lacks.

This document is the architecture decision for the COM11-side path the user
approved. It is **read-only analysis + offline design**. Nothing here opens
COM11, writes serial bytes, stops/restarts a service, edits a remote config,
injects AFT, or reboots. Live actions are gated and called out explicitly; the
**only** code shipped alongside this doc (`SasSerialEmulator.cs`) is a
**dry-run/no-write** scaffold that refuses to touch hardware by default.

Date of evidence: 2026-06-16 (read-only verified this session).

---

## 0. TL;DR / recommendation

- **Who generates `80`/`81`:** NOT CommCtrlSAS and NOT Aurum. The polls are
  generated by an **external SAS host/poller that reaches the cabinet over the
  COM11 serial line through the `VE MULTIPLEXER 4004145 SI 2CH` device**.
  CommCtrlSAS only **bridges** serial⇄loopback-TCP; Aurum is the SAS **slave**
  (it answers `00`). On `.90` that external poll stream is alive; on `.171` it
  is absent (MUX detected, station negotiated, but no poll bytes flow).
- **A local process cannot open COM11** — CommCtrlSAS owns it. So a true serial
  emulator must be an **external peer on the MUX**, or it requires
  **stopping/replacing CommCtrlSAS** (forbidden this round).
- **Least-invasive path that needs NO COM11 and NO service changes:** synthesize
  the host poll stream **into the existing loopback `31150 → Aurum` TCP
  connection** with the proven in-stream WinDivert technique (the same one that
  already lands `0x72`). The poll bytes (`1B80`/`1B81`) are **known verbatim**
  from `.90`, so we are not guessing protocol. This is the recommended Stage-1
  experiment. **It is a hypothesis until validated** (see §5/§6 risks).
- **Important correction to prior assumption:** `GetOverlappedResult error: 64`
  is **not** the serial fault. It is logged on `CSocketConnection::ReadToBuffers`
  (the loopback TCP sockets `3110…`/`3115…`) and it **also appears on the working
  `.90`**. It is normal socket-reconnect churn, not the COM11 problem.

## 1. Who generates the `80`/`81` polls — evidence

### 1a. On `.90` (works): polls flow CommCtrlSAS → Aurum; Aurum answers `00`

Read-only Stage-0 sniff `../captures/stage0-90-steady-20260616-141116.txt`
(`DIRLEGEND S2C=CommCtrlSAS->Aurum`):

```text
dir=S2C sport=31150 dport=56616 ... len=2 hex=1B81     # host poll relayed to Aurum
dir=C2S sport=56616 dport=31150 ... len=0 hex=-        # Aurum bare-ACKs the poll conn
dir=C2S sport=56615 dport=31100 ... len=1 hex=00       # Aurum slave reply 00 on 31100
dir=S2C sport=31100 dport=56615 ... len=0 hex=-        # CommCtrlSAS bare-ACKs the reply
```

Steady cadence ≈ every ~200 ms, `80`/`81` alternating (676 packets / 45 s).
`../captures/sas-response-table-steady.json` summarises it: poll `81` → `00`
(113×), poll `80` → **no reply** (112×). So the slave (Aurum) answers `81` with
`00` and stays silent on `80`.

This proves: **the poll byte enters CommCtrlSAS and is pushed out to Aurum.**
CommCtrlSAS is a relay; the poll originates upstream of it — on the serial side.

### 1b. On `.171` (broken): no `80`/`81` at all; Aurum just emits `01`

Read-only Stage-0 sniff `../captures/stage0-171-steady-20260616-144705.txt`:

```text
dir=C2S sport=64361 dport=31150 ... len=1 hex=01       # Aurum -> CommCtrlSAS keepalive 01
dir=S2C sport=31150 dport=64361 ... len=0 hex=-        # CommCtrlSAS only bare-ACKs
```

For the whole 30 s window (284 packets) there is **only** Aurum→`31150` `01`
and bare ACKs back. **Zero `1B80`/`1B81`. No `31100` slave-reply traffic.** The
passthru run `../captures/respond-171-passthru-20260616-150037.txt` confirms
`pollSeen=0` on `.171`.

The `.171` sasmsgr log corroborates: the last decoded SAS line is a stale
injected `0172…Transaction43` at `11:02`; there is **no steady `qGMID1:80/81`
stream** like `.90` has — i.e. Aurum sees no host polling.

### 1c. CommCtrlSAS itself does not synthesize the polls

`.171` `CommCtrlSAS\2026-06-16.log` shows the serial side **came up cleanly**:

```text
serial port \\.\COM11 open on baudrate 921600
CCommConnection::CheckForMux Detected: VE MULTIPLEXER 4004145 SI 2CH - 2.0.1
Listening on comm 11
CH 2
SA 1
Connection 3110000001 established on port 31100
Connection 3115000002 established on port 31150
```

So COM11 opened, the MUX answered `CheckForMux`, the station address (`SA 1`)
and channel (`CH 2`) negotiated, and the loopback listeners came up — **yet no
`80`/`81` is pushed to Aurum.** If CommCtrlSAS generated polls internally after
MUX/SA negotiation, `.171` would show them. It does not. Therefore the poll
source is **external to CommCtrlSAS, on the serial/host side behind the MUX.**

`CommControler.ini` is identical on both cabinets (`<11> <921600>`), so config
is not the differentiator.

### 1d. Role summary (verbatim from evidence, not assumed)

| Element | SAS role | Evidence |
|---|---|---|
| External device on COM11 (behind `VE MULTIPLEXER … SI 2CH`) | **HOST / poller** (emits `80`/`81`, originates `0x72` AFT) | polls enter CommCtrlSAS from serial and are relayed out to Aurum on `.90`; absent on `.171` |
| `CommCtrlSAS.exe` | serial⇄TCP **bridge** + MUX/station negotiation; owns COM11, `31100/31101/31150/31151` | `CommCtrlSAS` log; `AFT_Robustness_Findings.md` #6 |
| `GoldClub.Aurum.Services` (sasmsgr) | SAS **slave** (answers `00`, logs `qGMID1:`) | `.90` replies `00` on `31100`; bridge docs hop2 |

> **The `.171` root cause is the missing external host poll stream, not a serial
> open failure and not the (frozen) Aurum config.** `GetOverlappedResult error 64`
> is socket-churn noise present on `.90` too.

## 2. COM11 emulator architecture options

The shared constraint: **CommCtrlSAS already holds COM11 exclusively.** Win32
serial handles are not shareable, so a *second* local process cannot
`CreateFile("\\.\COM11")` while CommCtrlSAS runs — it will fail with sharing
violation. That single fact drives the option ranking.

| # | Option | Feasibility | Disruption | Risk | Service-ownership change required |
|---|---|---|---|---|---|
| A | **External serial peer on the physical MUX** (a real or emulated SAS host wired to the upstream/2nd channel of the `SI 2CH` MUX, polling `80`/`81`) | Possible — this is literally what `.90` has | Low on the cabinet OS (no local process), but needs **hardware/cabling** + a real SAS host poller | Medium: must sustain correct cadence, link-sync toggle, framing/CRC, and an interrogate state machine (see `hop1`) | **None on the cabinet.** Needs external kit. |
| B | **Local process replaces/stops CommCtrlSAS**, opens COM11 as host, and bridges to Aurum on `31100/31150` directly | Technically feasible | **High** — requires stopping CommCtrlSAS (**forbidden this round**) and re-implementing the bridge + MUX/station negotiation | High: wedges the live session; must reproduce `CheckForMux`, `CH/SA`, `0x1B` framing exactly | Stop CommCtrlSAS; take over COM11 + 4 ports. **Disallowed now.** |
| C | **Local virtual serial pair / null-modem** feeding CommCtrlSAS | **Not feasible without stopping/reconfiguring CommCtrlSAS** | High | High: CommCtrlSAS is pinned to the real `\\.\COM11` device via `CommControler.ini`; inserting com0com/virtual pair means changing the port and restarting the service | Reconfigure + restart CommCtrlSAS. **Disallowed now.** |
| D | **WinDivert loopback poll-injector** — synthesize `1B80`/`1B81` into the live `31150 → Aurum` TCP connection (server→client) using the proven in-stream seq-splice; let Aurum reply `00` on `31100` as usual | **PROVEN on `.90` (2026-07-09)** — txn 83/84, no physical polls | **Low** — purely loopback; bridge L0/L1 must be up | Medium: delta splice; drain after AFT to avoid TCP wedge | **None.** No COM11, no service stop. See [`no-physical-polls-layers.md`](../no-physical-polls-layers.md). |

### Recommendation

- **Primary (build/validate first): Option D**, because it needs no COM11, no
  service stop, no config edit, and reuses code paths already proven on this
  bus. The poll bytes are verbatim from `.90`, so no protocol guessing.
- **Fallback if D fails to bring Aurum online: Option A** (a real external SAS
  host on the MUX) — the faithful reproduction of `.90`. This is the only option
  that is "the real thing", but it needs hardware and is out of scope for code.
- **Options B and C are explicitly deferred** — both require stopping/replacing
  CommCtrlSAS, which is forbidden this round.

> Why D is not the same as the old `WdRespond` failure: `WdRespond` is a
> *slave responder* waiting to *answer* polls — and `.171` has no polls to
> answer (`pollSeen=0`). Option D is the **opposite role**: a *host poller* that
> *originates* `80`/`81` toward Aurum. Different direction, different job.

## 3. Direction model the emulator must reproduce (avoid the confusion in §5 of the brief)

On the `.90` loopback the observed directions are:

```text
HOST(serial)  --80/81-->  CommCtrlSAS  --1B80/1B81-->  Aurum        (S2C, port 31150 server->client)
Aurum         --00-->     CommCtrlSAS  --00-->         HOST(serial) (C2S, port 31100 + serial)
```

So to make Aurum behave as on `.90`, **whatever stands in for the host must
cause `1B80`/`1B81` to arrive at Aurum on the `31150` connection in the
server→client direction**, and must accept Aurum's `00`.

- **Option A** achieves this *correctly* by feeding real `80`/`81` into COM11;
  CommCtrlSAS does the `0x1B` framing and the `31150` push itself (exactly the
  proven relay).
- **Option D** *bypasses* CommCtrlSAS's relay and injects the already-`0x1B`-
  framed `1B80`/`1B81` straight onto the `31150 → Aurum` TCP stream. **Do not
  assume the serial-side host byte equals the bridge byte**: on the bridge the
  poll is `1B80`/`1B81` (the `0x1B` is CommCtrlSAS's framing prefix); on the raw
  serial line it is just `80`/`81` (no `0x1B`). Option A sends `80`/`81`;
  Option D injects `1B80`/`1B81`. This distinction is load-bearing.

## 4. Stage 0/1 for the COM-side path (what is safe, what needs the user)

### Stage 0 — passive, read-only (no user live action beyond what's done)

0.1 **Bridge sniff (DONE).** `.90` vs `.171` Stage-0 captures already prove the
poll-presence delta. No further capture strictly required, but a fresh `.171`
sniff can be re-run any time with `Invoke-Stage0SasSniff.ps1 -IP 10.0.0.171`
(SNIFF mode physically cannot inject).

0.2 **Passive serial sniff feasibility — LIMITED.** You **cannot** passively
read COM11 from a second local process while CommCtrlSAS owns it (no shared
read). Options for serial-side ground truth, in order of safety:
   - **(safe) Trust the bridge sniff** — CommCtrlSAS already decodes the serial
     poll onto `31150`; the loopback sniff *is* the serial poll, framed. This is
     the sanctioned source.
   - **(safe) Read CommCtrlSAS logs** for `CheckForMux`, `CH`, `SA`, and any
     poll/diagnostic lines (read-only over `c$`).
   - **(needs hardware, external) physical serial tap** on the MUX cable — only
     if Option A is pursued; out of scope for software.

0.3 **Port-ownership check (read-only, no stop).** Confirm CommCtrlSAS owns the
loopback ports and that `80/81` is truly absent on `.171` before any inject:

```powershell
# read-only: who owns the bridge ports + are there any polls right now
Get-NetTCPConnection -LocalPort 31100,31150 -ErrorAction SilentlyContinue |
  Select-Object LocalPort,State,OwningProcess
# (COM11 ownership is implied: CommCtrlSAS logs "serial port \\.\COM11 open".)
```

A **non-invasive COM11 open test** (open `\\.\COM11` read-only to prove it is
busy) is **deliberately NOT performed**, because even a benign open can perturb
a serial device and the result is already known from logs (CommCtrlSAS holds
it). Do this **only** if the user later authorizes stopping CommCtrlSAS — and
even then, prefer reading logs.

### Stage 1 — first live action (requires explicit user GO)

The first live action for the recommended path (Option D) is a **single
WinDivert poll-inject probe on `.171`**, time-boxed, observing Aurum's reaction:

1. Build the loopback poll-injector (a fork of `WdInject.cs`/`WdRespond.cs`
   splice plumbing — *not yet written*, see §5).
2. Run it for a short, bounded window injecting `1B81`/`1B80` at ~200 ms into
   the live `31150 → Aurum` connection on `.171`.
3. **Watch only** (read-only) the `.171` sasmsgr + WAT2AFT logs for:
   - `qGMID1:81`/`qGMID1:80` lines appearing (Aurum is now "seeing" polls), and
   - the `NO OWNED DEVICE FOUND FOR WAT … WILL NOW EXIT` loop **stopping**.

**GO gate 1:** Aurum logs the injected polls and the no-owned-device loop stops
for a sustained window. If Aurum ignores the injected polls (e.g. CommCtrlSAS's
real seq desyncs the stream, or Aurum validates a source the inject can't fake),
**stop and report** — that means Option D is insufficient and Option A
(external serial host) is required.

> No AFT/money is sent at Stage 1. The transfer (`Send-TestAft1000.ps1 -nr
> -Amount 1000`) only happens at the existing `171-landing-plan.md` Stage 4
> gate, after the session is demonstrably online.

## 5. Minimal poll-generator byte behavior (HYPOTHESES clearly marked)

These are the bytes/cadence a generator would emit. The **byte values are FACTS**
from `.90` captures; the **acceptance/cadence tolerances are HYPOTHESES** until a
live probe confirms them.

### Facts (verbatim from `.90`)

- **Bridge-framed poll bytes (Option D, loopback):** `1B 81` and `1B 80`
  (`0x1B` = CommCtrlSAS framing prefix + SAS general poll for address 1).
- **Raw serial poll bytes (Option A, COM11):** `81` and `80` (no `0x1B`).
- **Alternation:** `81` and `80` alternate (link-sync / wake toggle bit).
- **Cadence:** ~200 ms per poll on `.90` steady (≈ every 0.2 s, jitter to ~250 ms).
- **Slave replies observed:** poll `81` → `00`; poll `80` → *(silence)*.
  Single-byte, no CRC. (From `sas-response-table-steady.json`.)
- **General polls carry no CRC** (single byte). Only **long polls** (e.g.
  `0x72`) carry the CRC-16/KERMIT trailer — `Get-SasCrc16` in
  `Invoke-WinDivertAft.ps1` / `ReframeCrc16Kermit()` in `WdRespond.cs`.

### Hypotheses (must be validated, never shipped as truth)

- **[H1]** Injecting `1B80`/`1B81` into the `31150 → Aurum` TCP stream (Option D)
  makes Aurum treat the session as online. **PROVEN on `.90` 2026-07-09** — sasmsgr
  `qGMID1:80/81` @ 200 ms and txn 83/84 AFT ingest + credit without physical IGT.
- **[H2]** ~200 ms cadence is "fast enough" to hold online; the real link-sync
  timeout is unknown. Start at the observed ~200 ms; do not go faster.
- **[H3]** The send-delta splice on the server→client (`31150→Aurum`) direction
  stays stable long enough for Aurum to enumerate. A desync only RSTs the SAS
  link (recoverable), but may prevent reaching the owned state.
- **[H4]** No additional enumeration/capability long poll is needed beyond
  `80`/`81` for WAT2AFT to "own" the device. *If the no-owned-device loop
  persists after polls are accepted, capability/enumeration polls — which were
  NOT present in the `.90` steady capture — would be required, and those bytes
  are NOT known. Do not invent them; capture a `.90` bring-up first.*

The generator must **never** emit a poll value not present in the captures, and
**never** fabricate a long-poll/CRC body. If `80`/`81` is insufficient, the next
step is a fresh `.90` **bring-up** capture (service restart on `.90` only, the
one authorized state change in `Invoke-Stage0SasSniff.ps1 -Mode bringup`) to
record any enumeration handshake — not guessing.

## 6. Safety, guardrails, and what is/ isn't built

- **Shipped now:** this doc + `SasSerialEmulator.cs`, a **dry-run/no-write**
  scaffold (Option A shape). By default it **prints the poll plan and exits**; it
  **refuses to open any serial port** unless `--port COMxx --live --allow-write`
  are *all* passed *and* an explicit `--i-understand-live` token is given. Even
  then, on this cabinet it will fail to open COM11 (CommCtrlSAS owns it) — by
  design, that is the proof the local-serial path needs Option B/C.
- **Not built (by design):** the Option-D WinDivert loopback poll-injector. It
  is deferred until the user gives a Stage-1 GO, because its *first run is a live
  action on `.171`*. When approved, fork it from `WdInject.cs` (server→client
  in-stream inject) + `WdRespond.cs` (delta/ack-rewrite splice); inject only the
  verbatim `1B80`/`1B81`.
- **Forbidden and not done:** writing COM11, opening COM11 in write mode,
  stopping/restarting any service, AFT/money injection, remote config edits,
  reboot.
